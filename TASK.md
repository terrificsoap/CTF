# 10 — Сервис телеметрии лифтов КАРЕТКА (KRT-3) *(Pwn, 1000 pts)*

**Категория:** Pwn · **Объект лора:** концентратор телеметрии лифтов **КАРЕТКА**, контроллер
повозок **KRT-3** (`pwn.karetka.glub:1337`) · **Баллы:** 1000 · **Целевое время:** 160–240 мин
(самое тяжёлое задание сетки)

---

## Легенда (рабочая бумага следственной группы, Инцидент №12-К)

> Контроллер **KRT-3** — нижний уровень лифтового хозяйства «КАРЕТКА»: шахтные повозки,
> картотека линий, «архивная страница» последнего принятого кадра. По штатному регламенту
> KRT-3 поднят **root-агентом телеметрии** на лифтовом узле подземного объекта: он принимает
> кадры от пультов, ведёт реестр линий и пишет журнал очередей подъёмов.
>
> В инциденте 12-К сеть лифтового узла прошла дальше, чем должна была: после остановки
> **службы очередей** (journalctl на узле обрывается на 03:41) зафиксирован подъём привилегий до
> root, а из призового тома `/srv/karetka/awards/12-K/` — который следственная группа
> смонтировала в стенд как доказательство, — ушла одна страница. Ключ к этому даёт сам сервис:
> две проверки в его коде сделаны не в тех единицах, в каких написан вызывающий код.
>
> Следственной группе передана **доказательная копия** сетевого сервиса KRT-3 (evidence copy):
> бинарник, его unstripped-вариант и ровно та `libc.so.6`, против которой он собран. Копия
> поднята на стенде как живой TCP-сервис — поведение, которое вы получите на стенде, побайтово
> соответствует собранному ELF.

## Что дано

Три файла в `artifacts/` — контрольные суммы реальные, пересчитаны `shasum -a 256` по выданному
комплекту; полная таблица — в `artifacts/sha256.json` (566 байт, полный список хешей выданного;
себя в него не включает).

| файл | роль | размер, байт | sha256 |
|------|------|-------------:|--------|
| `karetka` | strip-копия сервиса, которую получает игрок | 7 200 | `abc7d7c9b1bf7a08b0f89dfa03975abc27605bfc4d1ec2e454175159fc35f63a` |
| `karetka.unstripped` | тот же код с `.symtab` + DWARF: символы раскладки (`arch`, `lines`, `ctx`, `cmd_rename`) | 20 712 | `ff5ed934bc591b1a7a827cf7d72bccae06020ce9ed0da222bc90b3fd6a71cf0b` |
| `libc.so.6` | та же библиотека, против которой собран бинарник (glibc 2.36-линейка, `ET_DYN`); источник смещений функций и гадов | 1 926 232 | `6b4a45352fd0c540a9c7c718f35ce8c8e46a4e482f9d3885a910c32d1a0e1421` |

Онлайн-сервис — TCP: образец на стенде **`127.0.0.1:1337`**, в бою — **личный инстанс каждой
команды** (свой порт, свой экземпляр процесса; адрес выдаётся вместе с токеном).

При подключении сервис печатает ровно две строки баннера:

```
KARETKA KRT-3 LIFT TELEMETRY // INCIDENT 12-K EVIDENCE COPY
CMDS: 1=LIST 2=ADD 3=RENAME 4=AUDIT 5=MIRROR 6=NOTE 7=REPEAT 8=STATUS 0=QUIT
```

Дальше — диалог packet-запросами; их кодировка в условии не приводится, её надо снять с
собственного ELF (стартовый адрес `0x10017b0`, `ET_EXEC`).

## Цель

Получить выполнение кода в сервисе и считать из призового тома страницу-доказательство
`/srv/karetka/awards/12-K/` — то есть флаг.

## Формат флага

`GLUB{[a-z0-9_]{6,48}}` — осмысленная lowercase-метка. Флаг существует **только** в памяти
процесса сервиса (в файл тома он не пишется) и приходит **только** как ответ `read(2)`/`write(2)`
перехваченного потока. В байтах выданных `artifacts/` его нет (проверьте `strings`/`grep`
`GLUB{`).

## Чего НЕ дано

- Исходников сервиса — только собранные ELF.
- Описания протокола: формата пакетов `2 ADD` / `3 RENAME` / `5 MIRROR` / `6 NOTE`, значений
  полей, кодировки смещения в `MIRROR`, границ «служебного» тега. Всё это добывается из
  `karetka`/`karetka.unstripped`.
- Смещений функций и гаджетов — ни в каком виде. Смещения внутри `libc.so.6` игрок считает сам
  по своей копии библиотеки.
- Таблица символов libc — только `dynsym` той самой `.so`; статической линковки нет, `open`
  в PLT у сервиса **отсутствует** (в `karetka` импортируются ровно три JUMP_SLOT: `read`,
  `write`, `_exit`).
- Готового стенда с gdb/qemu: на инфраструктуре турнира сервиса не отдаёт ни debugger, ни
  shell-доступа к хосту.
- Гарантии, что у вас есть pwntools: цепочка собирается из stdlib (`socket` + `struct`) или
  любым удобным инструментом — требование только к корректности байтов на проводе.
- Никаких «подсказок в banner»: `STATUS` сообщает путь тома, но не его содержимое; список
  страниц тома открывается только самой цепочкой.

## Ограничения инфраструктуры

- **Личный инстанс.** Каждый участник получает изолированный процесс сервиса; чужие соединения
  не влияют на ваш экземпляр.
- **Перезапуск и ASLR на соединение.** Каждое новое TCP-соединение обслуживается отдельно,
  базы `libc` и стека случайны **на каждое соединение**: адреса, утеченные в одном коннекте,
  недействительны в следующем. Обрыв соединения/падение процесса — начинать заново.
- **Лимит ввода:** 8 192 байт (0x2000) входящего потока на соединение — сверх него поток
  обрывается.
- **Бюджет:** 4 000 000 эмулируемых инструкций и 25 секунд на соединение; истечение — `exit`
  без вывода.
- **Стек NX, W^X, Full RELRO:** своего кода на стеке разместить нельзя; `mmap`/`mprotect`
  с `PROT_EXEC` → `-EPERM`; `.got.plt` после релокаций только для чтения.
- **Системные вызовы:** `execve`, `fork`/`vfork`/`clone`, `socket`/`connect`/`bind`/`listen`,
  `kill`, `wait4`, `ptrace` → `-ENOSYS`; `open` с флагами записи (`O_WRONLY|O_RDWR|O_CREAT|
  O_TRUNC`) → `-EACCES`; неизвестный путь → `-ENOENT`. То есть шелл-кода, outbound-соединения
  и «подложить файл» не получится: читается только по точному пути из тома.
- **Сервис пишет трассу вызовов.** По каждому соединению ведётся witness-журнал (RIP на
  переходах цепочки + список syscall с аргументами). Он используется для разбора решений и
  для проверки, что флаг напечатан цепочкой, а не угадан.
- **Нельзя:** флуд и DDoS (более 2 одновременных соединений от команды — только по запросу
  оргкомитета, организатор не тестировал поведение под сотнями соединений), сканирование
  соседних инстансов, brute-force по путям тома, попыток «прочитать память процесса» вне
  протокола.

## Тайминг

Ориентир сильной команды (суммарно 160–240 мин):

1. обратка протокола и раскладки — 30–45 мин;
2. утечка (`MIRROR` → GOT → база libc) — 35–50 мин;
3. перехват управления в `3 RENAME` (расстояние до сохранённого RIP) — 30–45 мин;
4. ROP-цепочка в libc без своего кода — 40–60 мин;
5. воспроизведение на свежем соединении с путём из `.listing` — 15–25 мин.

Ожидаемое число решивших на финале (~40 команд): **1–4**.
